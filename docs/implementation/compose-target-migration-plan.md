# Compose 靶场与沙箱网络接入：分步重构计划

状态：第一、二轮独立 Go 模块和第三轮平台接入代码已实现，真实 Compose 生命周期与本地模拟 Worker／浏览器流程已通过。完整网络通信验收仍待具备权限的本地环境执行；新模式默认关闭，不自动切换生产。本文以 `1f71c84` 的实现为基线，指导后续小步开发。未连接 VPS、清库或自动部署。实现见 [本机实验网络第一轮](lab-network-local.md)、[Compose 运行器第二轮](compose-runtime-local.md) 和 [平台接入第三轮](compose-platform-integration.md)。

## 目标与取舍

把“一份镜像对应一个容器”升级为“一份部署包对应一套 Compose 靶场”。学员得到独立容器、网络和可写数据，镜像共享。管理员导入已有部署文件，不再手工复写服务定义。

首版网络采用同机接入：Docker 创建每实例独立的 `internal` bridge 网络，Worker 将攻击沙箱的额外网卡接入选定的实验网络。保留沙箱现有 `eth0`、默认路由和出口策略，不通过共用靶机网桥跨桥路由。

这样减少跨桥转发配置，但仍需要管理地址、接线归属、异常清理和宿主机保护。`internal: true` 不等于隔离宿主机，不等于沙箱不能代理流量，也不让手动接入的沙箱自动获得 Docker DNS。

当前只实现同机接入。为网络接入保留明确接口，不提前实现 overlay、二层隧道、远程 Docker、Kubernetes、多运行器自动切换或网络管理微服务。

- 不重写 Btrfs 沙箱运行时、CLI／GUI 或内容 Git 同步。

## 最终模型

### 部署包与准备产物

部署包包含选定的 Compose 文件及其配套文件。以后可来自 Git 仓库目录或上传 ZIP；单独 YAML 仅在不依赖其他文件时足够。

```text
vulnerable-app/
├── compose.yml
├── Dockerfile          # 有构建需求时使用
├── app/
└── init.sql
```

解析后保留服务、依赖、健康检查、命令、环境变量、网络及卷的语义，生成经过平台校验的运行配置。平台负责项目名、网络名、地址池、资源限制、归属标签、日志限制和入口；不能无提示地丢弃不支持的字段。

准备任务产生不可变部署标识，绑定包内容摘要、规范化运行配置及实际镜像摘要。准备情况按节点记录，不能因为一个节点准备成功就允许所有节点启动。学员启动使用已准备产物，禁止隐式 pull、build 或拉源码。

模板只指向当前启用的产物。更新模板影响后续新实例，已运行实例继续引用原产物，不引入面向管理员的历史版本编辑器。仍被实例引用的产物不能提前删除。

### 实例与服务

```text
模板 → 已准备部署 → 用户的 Compose 项目实例
                         ├── 服务容器
                         ├── 项目网络
                         ├── 实例数据卷／可写文件
                         └── 沙箱接线（可以暂时没有）
```

实例状态与服务健康分开：创建中、运行中、清理中、已释放、异常；健康信息单独说明哪些服务尚未就绪。Compose 成功创建容器不等于应用可用，无健康信号时返回未验证。一次性初始化服务正常退出不能被误判为整个靶场失败。

释放的业务含义仍是删除这一实例的资源和数据；不删除共享镜像、部署包或其他实例。项目归属不能只靠可冲突的名称判断，所有容器、网络、卷和文件都需有可核验归属。

### 本机网络接入

```text
攻击沙箱
├── eth0：现有沙箱网络与默认路由
└── 实验网卡：仅有实验子网的直连路由
                    │
         当前实例的 Docker internal 网络
                    ├── Web
                    └── 其他可访问服务
```

- 使用 Compose 原有多网络拓扑；沙箱接入管理员选定的网络，不默认暴露后端数据库。不支持的网络驱动明确报错。
- 平台从节点专用、无冲突地址池分配子网。不能强制多份实例复用上游写死的子网或固定 IP；依赖硬编码地址的项目需显式适配。
- Docker 分配容器地址，Worker 为沙箱接线预留不被 Docker 动态分配的地址；Docker IPAM 排除范围与 Worker 账本必须一致。
- 一份沙箱可能连接多个实例：网卡名按接入记录生成，不固定使用唯一 `eth1`；不同实验子网不得重叠。容量受节点接线和总资源限制约束。
- 不修改沙箱默认路由，不开启平台提供的跨网转发或 NAT。靶机反连使用沙箱实验地址；不承诺阻止有权限的学员主动在沙箱中代理流量。
- 保留项目网络到宿主机服务的访问限制，不依赖 `internal` 替代宿主机 INPUT 保护。规则由一个网络模块管理，不跨多个模块拼接。
- 第一版展示实际服务 IP 与端口。Docker 容器间服务名解析正常保留；沙箱名称映射单独实现，暂不新增 DNS 服务。

接入接口只表达 `Attach(沙箱身份, 实例身份, 网络选择)`、`Detach(接入身份)`、`Reconcile(本地实际资源)`。实现绑定沙箱 ID、网络命名空间身份和实例代次，防止 PID 复用后接错环境，不把瞬时 `/proc/<pid>` 路径当永久身份。

当前唯一实现是本机 veth。未来远程接入需要额外隧道或路由和对应放行规则，不能声称 `internal` 网络天然支持远程访问。

## 第一轮：验证本机接线与隔离边界

只新增网络接入模块和本地实验夹具，不切换现有生产路径，不改后台。模块职责保持聚合，测试夹具不演变为第二套部署服务。

交付：

1. 用自带夹具创建一个 `internal` 网络和测试靶机，将测试沙箱命名空间接入该桥。
2. 实现地址预留、实例绑定的接口名、重复接入幂等、断开与失败回滚。
3. 核实 bridge 转发、Docker 过滤规则与现有 Worker 规则的实际交互；不能只根据配置推定互通。
4. 将宿主机保护扩展为可识别项目网络；明确保留哪些规则，哪些旧跨桥例外将在最终切换时删除。

验收：

- 沙箱可访问靶机 TCP／UDP，靶机可主动反连实验网 IP，双方看到真实源地址。
- 原 `eth0`、默认路由和沙箱允许的公网访问不变；靶机直接公网出口受阻，宿主管理测试端口不可访问。
- 用户 A 不接入用户 B 网络；验证跨项目访问限制，不能把“各有一座桥”当作已完成隔离的证明。
- 多实例地址不冲突，重复接线不产生重复接口，断开不影响其他实例或主网卡。
- 覆盖失败回滚、孤儿网卡识别、命名空间消失及身份变化。真实网络验收需有 NET_ADMIN 的本地环境；模拟通过不能替代此门槛。

本轮结束只确认网络方案可用。缺少真实网络验证条件时，在记录中明确未验收，后续可继续无关解析工作，不启用生产切换。

## 第二轮：Compose 项目运行器与生命周期

代码与本机真实 Compose 生命周期验证已完成，详见 [Compose 运行器第二轮](compose-runtime-local.md)。沙箱接线通过独立生命周期接口对接，实际 Worker 控制通道与 RuntimeManager 尚未切换；第一轮真实网络验收仍保留为生产切换门槛。

用仓库内置的双服务测试包运行完整链路，暂不新增公共导入 API 或重做后台。

交付：

1. 使用 Compose 官方 Go 解析库及固定、经过测试的 Compose v2 CLI；不自行实现 Compose 服务编排。启动检查版本和功能，Worker 只连接本机 Docker Socket。
2. 运行器提供准备、启动、检查、释放接口；明确控制端传入部署身份，不能传任意宿主路径、Shell 命令或 Docker 参数。调用使用参数数组，不拼接 shell；隔离继承环境，避免部署服务器的环境变量意外参与 Compose 插值。
3. 第一版支持 `image`、服务依赖、健康检查、命令与环境变量、项目内网络、命名／匿名卷及包内只读文件。先不支持源码构建，遇到 `build` 返回明确不支持，第四轮再启用。
4. 实例具有唯一 Compose project 名称。去除或规范化上游固定 `container_name`、显式资源名；禁止固定宿主端口映射，入口使用容器地址。变更在解析报告中可见。
5. host 网络、外部共享资源、Docker Socket、宿主路径及特权设备不进入普通模板。`include`、远程 `extends`、profiles 等首版未支持特性明确拒绝；不是宣称完整兼容任意 Compose。
6. 总资源预算按整套项目计算，落实为各常驻服务的实际限制；不能简单地给每个服务复制原单容器额度。限制服务数、并发准备数、日志和实例数，启动时核验预算。
7. 接入第一轮模块，打通先启动沙箱或先启动靶场两种顺序。靶场可在尚无攻击沙箱时运行，响应中分别给出靶场状态和接入状态，不能虚报已连接。
8. 沙箱创建后重建其应有接线；沙箱销毁只断接线，保留未到期靶场。Worker 当前会在重启时清理残留沙箱，不能假定原 namespace 仍然存在。
9. 延续现有持久账本和停止墓碑，扩展到项目资源及接线；接线清理成功后再删除项目网络，清理失败不返回已释放。
10. 操作按实例串行、节点有界并发；长启动／准备不持有全局生命周期锁。停止和到期意图可取消或压过启动，不能让一个卡住的数据库阻塞所有用户释放。

验收：

- 双服务能通过 Compose 服务名通信；两个用户使用相同模板时容器和数据互不共享。
- 健康检查、初始化退出、部分启动失败分别报告；重复启动不重建、不续期。
- 手动释放、到期、Docker 不可用、Worker 重启、启动与释放竞争最终收敛；迟到启动不复活旧 ID。
- 只清理已验证归属的资源；失败不得调用宽泛 `prune` 或无差别清理同名资源；释放后镜像仍在。
- 复用现有 Worker 扫描和控制端对账，不增加按服务或按接线的后台定时器。

## 第三轮：后台导入与学习／挑战前后端闭环

代码已实现，本地 PostgreSQL＋模拟 Worker＋Chromium 流程已通过。控制通道、包下载与沙箱生命周期采用显式开关接入，真实网络验收前不启用生产；操作与限制见 [平台接入第三轮](compose-platform-integration.md)。

这一轮交付实际可用的管理员流程，先支持 ZIP 部署包和不依赖附件的 Compose YAML；不要求管理员填写 VPS 路径。

后台流程：

```text
上传 → 自动识别 Compose → 展示解析结果／问题
     → 确认入口、变量、资源和接入网络 → 保存
     → 选择节点准备 → 准备成功 → 启用并关联学习／挑战
```

交付：

1. 新建独立的 Compose 模板表单和服务端解析流程，避免在原单镜像表单中不断嵌套条件。管理员沿用现有布局，服务列表为只读识别结果，主要配置项保持精简。
2. 上传限制文件数、解压后大小和路径；拒绝目录穿越、符号链接和包外引用。部署包放在持久目录，具有摘要与受控的 Worker 下载机制，不通过公开静态目录分发敏感配置。
3. YAML 没有附件也可导入；存在 `./init.sql` 等缺失文件时指出具体路径，不等学员启动才失败。第一版附件挂载只允许包内只读文件；需要可写目录的项目使用实例卷，或等待第四轮实例副本支持。
4. 更新模板、准备任务、实例和接入所需数据结构及协议。建议概念为 `target_templates`、不可变部署产物、按节点准备记录、`target_instances`；接线账本先落在 Worker，不为每张网卡增加独立平台 CRUD。
5. 保留模板 ID 及学习／挑战关联字段。运行结果支持服务数组和入口数组，不能只返回任意一个容器 IP；内部依赖默认不作为主要入口。
6. 管理员手动查询准备状态与查看脱敏日志，不新增定时轮询。启动／释放响应、已有 Worker 心跳与必要的最小状态通知用于更新页面；断线重入读取一次数据库快照，不重复发送启动。
7. 共用 `TargetEnvironment.vue` 展示一个环境按钮、倒计时、主要入口；服务明细展开查看。状态区分“靶场已运行但沙箱未接入”，不增加逐服务启停按钮。
8. 在 Worker 协议中公布 Compose 及网络接入能力。首版仅允许同机；不兼容或未准备的节点返回明确原因，不偷偷回退旧单容器路径。

验收：

- 管理员从上传到准备、启用、关联课程，再到学员启动／释放，全链路可用。
- 缺附件、变量缺失、资源超限、不支持的 Compose 字段、节点未准备均在相应阶段明确反馈。
- 非管理员不能导入／准备；学员只能操作自己且有内容访问权限的实例，不能注入节点、路径、Owner 或部署配置。
- 重复点击、并发编辑、页面刷新、控制连接中断不创建重复实例，不自动延长租期。
- 本地 PostgreSQL、模拟 Worker、Chromium 与真实本机 Compose 夹具分别验证；模拟结果不描述为真实网络验收。

## 第四轮：Git 来源、构建和配套文件

这一轮覆盖常见开源靶场的完整来源流程；不与第三轮同时扩展。

交付：

- 添加 Git 仓库、分支、目录、Compose 文件选择；仓库拉取后固定到提交，保留构建及挂载需要的目录结构。不执行 Git hooks 或仓库附带安装脚本。
- 保留 ZIP 与 Git 两种来源，形成同一种部署包。GitHub 私库认证可复用教程同步的加密凭据基础设施，但靶场来源、权限和同步任务独立，不让教程凭据默认获得构建权限。
- 在管理员准备阶段支持包内 Dockerfile／本地 build context；构建后记录具体镜像。远程 context、额外特权构建、构建凭据等未支持项明确拒绝。
- 私有镜像仓库认证与 Git 凭据区分，凭据不写入公开 Compose、命令行、产物或日志。构建输出、Compose 解析输出与 API 错误都要防止暴露环境变量密钥。
- 构建、拉取需要的联网仅发生在准备阶段，与运行期靶场禁止公网出口分开控制。第一版构建只接受管理员审核的包，不开放普通用户任意构建。
- 需要包内可写文件时，创建实例独立副本或初始化实例卷；禁止多个用户写同一份部署包。资源回收包含这些副本。
- 明确准备的超时、取消、失败重试与节点磁盘压力行为；沿用已有有界任务机制，不新增通用任务平台。

验收使用一个含 Web、数据库、初始化文件和本地 Dockerfile 的夹具：从来源准备成功，学员冷启动不触发任何下载／构建，重复实例数据独立，更新模板不替换运行实例。

## 第五轮：切换旧模板并删除旧路径

逐步开发不意味着永久运行两套靶场系统。切换前保留旧生产路径，只在开发验证中启用 Compose；完整验收后安排一次维护切换。

1. 暂停旧实例新建，等待现有实例释放或到期；确认数据库与旧 Worker 账本没有未清理责任。清理未完成时不能删状态文件或旧执行器。
2. 现有单镜像模板转换成单服务 Compose，保留模板 ID、名称、说明、入口及学习／挑战关联，不实现旧运行实例的在线转换。可提供一次性离线转换命令，无需长期兼容层；全新环境可直接重建模板。
3. 准备新产物，完成与旧模板等价的功能验证，再切换学习／挑战启动入口。控制端与 Worker 同次部署，旧 Worker 能力不足时明确拒绝操作。
4. 删除旧单容器 Docker API 运行器、单镜像准备接口与旧表单；协议、类型、测试和配置同时清理，不保留隐藏 fallback。
5. 在旧网络无资源引用后删除项目原有共享靶机桥及对应跨桥规则；不删除沙箱网桥，不动非本项目 Docker 网络。
6. 更新部署依赖、持久目录、备份要求、资源配置和运行文档。数据库按已确认的部署方式调整，不承诺保留用户自行清空的数据；不会未经指示执行清库。

切换完成后只有一个 Compose 执行路径，简单单镜像靶机也使用该路径。最终移除当前 `image`／`ports` 作为运行事实来源的字段及单容器响应约定。

## 分机部署的后续边界

不纳入以上五轮，但这些约束现在必须成立：

- 模板与学习业务不依赖本机网桥名、网络命名空间路径或 Docker Socket；业务只接收实例和服务入口。
- 沙箱、Compose 和接入能力独立声明，当前同一个 Worker 程序可承载全部职责。以后 Docker-only 节点不应为了接入平台而初始化 Btrfs 沙箱。
- 调度以可用接入能力为边界，当前能力只表达同机可达。远程能力上线前，对分机请求明确拒绝，不能因登记同一名称的网络域就假定连通。
- 未来另行实现跨主机路由或隧道，包括节点唯一地址范围、回程路由、宿主机保护及 `internal` 网络转发规则适配。必须真实验证反连和出口策略。

这能保留上层业务和 Compose 生命周期接口，但不承诺分机零代码改动，也不提前建设远程网络。
